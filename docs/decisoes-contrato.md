# Decisões do contrato

Fecha as questões abertas listadas em [`spec-gaps.md`](spec-gaps.md). **Nada aqui altera a SPEC.md**:
o que depende de mudança na SPEC está na seção 3, para a sessão 1 aplicar. Qualquer item pode ser vetado;
a coluna "Como mudar" diz o que precisa ser alterado.

**Resumo**

1. D-01 a D-04 são **suas**: 3 níveis, 8 temas, nomes dos 4 tipos e o formato do `/health`. As demais (D-05 em diante) são **minhas**.
2. Critério das minhas: a opção mais simples que um teste consegue verificar sem adivinhar nada.
3. Códigos de erro, status HTTP e formato dos payloads estão fechados e **exatos** nos testes (`contrato.py: ERROS`, `checar_erro`).
4. Os nomes de módulo, o schema e os `data-testid` seguem concentrados em `contrato.py`, `contrato.ts` e `evals/exercicio.schema.json`.
5. Várias escolhas minhas coincidem com o que a API de referência descartável já fazia, então "ela passa" não prova que são as melhores (ver seção 2).

Legenda de autoria: **[VOCÊ]** decisão sua; **[CLAUDE]** decisão minha.

## 2. Cuidado ao ler "a referência passa"

A API de referência descartável (escrita por um agente que viu os testes) passa os 153 testes da API.
Mas várias decisões acima (D-14, D-15, D-16, D-24) foram **tiradas do comportamento dela** quando a spec
era omissa. Passar prova que o contrato é satisfazível e coerente, não que é o melhor.
